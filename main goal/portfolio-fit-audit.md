# Соответствие портфолио вакансии Larian Studios

Дата проверки: 2026-10-04.

Цель проверки: определить, стоит ли развивать существующий Game Companion QA проект для отклика на Junior Web Dev QA Analyst и какие результаты должны быть видны на GitHub.

Источники: [сохранённая вакансия](larian-qa.pdf), [официальная страница Larian](https://larian.com/careers/5bd314b3-0fcd-4dc1-9097-410d7b3f51cd), [форма отклика](https://jobs.lever.co/larian/5bd314b3-0fcd-4dc1-9097-410d7b3f51cd/apply), все шесть существующих Markdown-документов проекта, локальная история Git и проверка удалённых веток. Это оценка данного репозитория, а не всех навыков кандидата или остальных его проектов.

## Вывод

**Идея проекта соответствует вакансии. Текущее содержание является подготовкой портфолио, но ещё не демонстрацией выполненной практической QA работы.**

Game Companion предоставляет подходящий объект для проверки веб-интерфейса, HTTP/API, сохранения данных, автоматизации и доступности. TypeScript, Playwright и SQLite позволяют показать значительную часть нужных навыков. Для полезности проекта важны проверяемые результаты: запущенные тесты, расследования, исправления и регрессия.

Начинать заново или создавать большую игру для этой цели не требуется. Следует сохранить основу, перейти к исполнению и добавить несколько адресных доказательств. Выполнение всего текущего плана тоже не обеспечит автоматически полного соответствия: отдельные темы вакансии в нём не отражены.

## Что фактически есть сейчас

До добавления этого аудита в рабочей папке были шесть Markdown-документов и PDF вакансии. В документах найдены:

- 25 требований с `REQ-` ID;
- 19 ручных сценариев с `SCN-` ID;
- 21 запись предполагаемой автоматизации с `TEST-` ID;
- 27 именованных вариантов проверки email.

Записи инвентаря, варианты входных данных и запуски в разных браузерах являются разными величинами. Число 21 не означает 21 выполненный тест.

Есть [план проекта](../PROJECT_PLAN.md), [требования и риски](../test-docs/requirements-and-risks.md), [стратегия тестирования](../test-docs/test-plan.md), [ручные сценарии](../test-docs/test-scenarios.md), [матрица покрытия](../test-docs/traceability-matrix.md) и [план работы в чатах](../test-docs/chat-task-plan.md). Стратегия и сценарии прямо обозначают отсутствие реализации и выполнения.

Не найдены README, приложение, пакет зависимостей, исходники тестов, конфигурация Playwright, CI workflow, SQL-файлы, отчёты об исполнении, результаты исследовательского тестирования, баг-репорты и материалы расследований. Поэтому оценить качество кода, устойчивость автоматизации и реальные результаты пока невозможно. Автотесты в рамках аудита не запускались: запускать пока нечего.

При проверке удалённого Git репозитория:

- ветка по умолчанию — `main`, коммит `2d8761e848324957c13ffcc3e6be0d309e299e6f`; её дерево содержит только `PROJECT_PLAN.md`;
- при заключительной проверке удалённая `documentation` указывает на `21e4efc93e476b1024a30f5e1c47f187d8225bb5`;
- в начале аудита все шесть локальных документов имели незакоммиченные изменения; за время проверки они были закоммичены и опубликованы в `documentation` внешним действием. Аудит эти операции не выполнял.

Следовательно, ссылка на корень GitHub сейчас не показывает работодателю подробную версию из `documentation`. Перед откликом нужные результаты должны быть доступны по прямой ссылке и представлены в основной ветке либо в явно указанной ветке. Аудит ничего не коммитит, не переносит между ветками и не публикует.

Отдельно обязательные требования следует отличать от пожеланий. Например, отсутствие GitLab сейчас менее существенно, чем отсутствие работающей автоматизации и доказательств расследования ошибок. Вакансия не предписывает Node.js, MySQL, конкретное количество тестов или полноценную сертификацию на всех устройствах.

В форме отклика предусмотрено поле Portfolio URL, включая GitHub; оно не помечено обязательной звёздочкой, которой помечен CV. Это основание использовать портфолио как доказательство навыков, но из опубликованной формы не следует обязательность разработки отдельного большого пет-проекта.

## Что уже стоит сохранить

1. Разделение требований, ручных процедур, автоматизации и результатов. Статус «planned» указан честно.
2. Риски потери данных, ошибочных результатов и скрытых отказов API. Эти ситуации пригодны для содержательного QA рассказа.
3. Проверки данных в БД и негативные API случаи, а не только проверки видимости элементов.
4. Детерминированные данные, отдельные базы для опасных сценариев и планы диагностики сбоев автоматизации.
5. Доступность, клавиатура и восстановление после сетевой ошибки.
6. Различение настоящих дефектов и контролируемых симуляций. Минимальное число «найденных багов» не должно заставлять создавать вымышленные находки.

## Где сейчас можно потратить время без соразмерного результата

Документы уже намного подробнее имеющейся практики. Дополнительные раунды редактирования формулировок, всех правил email или сброса БД имеют меньший приоритет, чем первый работающий тест и зафиксированное расследование.

21 запись с многочисленными вариантами — внутренний объём проекта, а не требование работодателя. Полная реализация сброса БД с откатом и всех вариантов в трёх браузерах полезна, но существенно расширяет работу. Разумно сначала получить завершённый небольшой пример и только затем расширять покрытие. Это рекомендация промежуточного этапа; существующие критерии завершения проекта этим аудитом не изменены.

План работы с чатами помогает организации, но не должен стать главным материалом для работодателя. На входе нужны результаты и удобная навигация. Игровая тематика поддерживает контекст заявки, но не заменяет демонстрацию QA навыков.

## Рекомендуемый следующий этап

**Первый этап: один работающий фрагмент от приложения до доказательства проверки.** Использовать уже предложенный в PROJECT_PLAN первый этап: каталог, поиск/фильтр, детали и фиксированные API данные. Добавить ручное исполнение нескольких сценариев, минимальные UI/API автотесты, реальный CI запуск и короткий README с воспроизводимым запуском. Числа тестов на этом этапе не являются критерием готовности всего портфолио.

**Далее: закончить небольшой QA пакет.** Реализовать остальные выбранные функции, пять существующих smoke путей и приоритетную регрессию; выполнить браузерные и мобильные проверки, добавить SQL результаты и отчёт. Связать расследование, исправление и повторную проверку через задачу и PR. Если настоящего дефекта не найдено, честно сохранить SIM расследование отдельно; не представлять известный заранее дефект как самостоятельную находку.

**После практического ядра: закрыть адресные пробелы.** Добавить матрицу ОС/устройств с фактическим объёмом покрытия, привязку ручной доступности к WCAG, работу с GUI БД и задачами. GitLab и краткий gameplay кейс повышают точность соответствия, но не должны задерживать получение основного рабочего результата. Для GitLab достаточно небольшого выполненного примера, а не полного переноса проекта с GitHub.

Перед отправкой ссылки работодатель должен легко найти:

- короткий английский README: назначение, что лично сделано, запуск и ссылки на доказательства;
- исходники работающего приложения и тестов;
- фактический CI результат и отчёт, доступные по указанным ссылкам;
- несколько ручных результатов и полезное расследование;
- связанный пример изменения и проверки регрессии;
- запросы к БД, результаты доступности и точное описание браузеров/платформ/устройств;
- небольшое сопоставление навыков вакансии с конкретными файлами и результатами.

Публичная версия не должна выдавать планы за выполненную работу или закрытый доступ к отчёту за доступное работодателю доказательство. Сильное портфолио здесь — компактный проверяемый пример QA работы, который кандидат может объяснить на интервью.

## Точность технических утверждений

- Проверка ширины 375 px показывает поведение адаптивного интерфейса при таком viewport; она не доказывает работу на физическом телефоне. Встроенный WebKit Playwright также не равен запуску брендированного Safari. См. [документацию браузеров Playwright](https://playwright.dev/docs/browsers).
- Для конкретных критериев доступности использовать [официальный справочник WCAG](https://www.w3.org/WAI/WCAG22/quickref/). В этом аудите не заявляется соответствие приложения WCAG: приложения и результатов проверок пока нет.
- Вакансия оценивается по опубликованному описанию. Полный набор личных качеств, командный опыт и возможность работы в офисе нельзя установить только по содержанию GitHub.

## Границы выполненной проверки

Прочитаны существующие документы и официальное описание, визуально просмотрены страницы PDF с обязанностями и требованиями, проверены инвентарь файлов, история, удалённая ветка по умолчанию и её содержимое. Создан только этот отчёт. Проверка не включала запуск приложения, автотестов или CI, подачу отклика, создание внешних задач, PR, коммиты, публикацию или изменение существующего плана.
